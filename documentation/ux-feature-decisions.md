# UX feature decisions

How particular features look and behave (the launcher, teams, views, records, email admin), with the reasoning behind each and what was rejected. Add an entry when a feature's UX decision is made or reversed.

Style choices that hold on any page (colors, tokens, surfaces, containers, chrome, help text, settings-page patterns) go in [ui-style-decisions.md](ui-style-decisions.md).

These entries are also the rules for their feature, with the components it's built from; [layers/core/DESIGN.md](../layers/core/DESIGN.md) doesn't repeat them. A decision here that other pages should follow also gets a rule in DESIGN.md.

## Launcher, rail and admin shell

- **Personal apps sit after org apps.** The collapsed rail separates them with the same plain divider it uses under the home icon (it's too narrow for a label); the expanded rail uses `<USeparator label="Personal">`; the launcher popover uses `<USeparator label="Personal">`; dashboards use a "Personal" heading. On a personal app's pages the rail and org switcher keep showing the last active org, so leaving the app returns to it.
- **Leaving admin**: the admin sidebar (desktop and mobile drawer) opens with a "Back to apps" link above the sections, and the admin header's top-right is a plain × button to the launcher.

## Teams

- **Limiting a container to teams is one field, "Who can see it", in the container's own create and settings forms** (`TeamAccessField`): everyone in the org, or only certain teams, then a multi-select of teams. It offers the caller's own teams (every team for holders of `<app>.all_teams`) and keeps teams already on the container listed even when the caller can't pick them, so a save never silently drops one. It renders nothing unless the org runs teams and the caller has a team to pick (or the container is already limited), so orgs without teams never see it.
  - A separate share dialog, like personal apps' `ShareDialog`, was rejected: team restriction is a property of the container that its editors change alongside its name, not a list of people.
- **"Show all teams" is a switch in the app's own chrome** (`ShowAllTeamsToggle`), off by default and remembered per app in a cookie the server reads, so admins get the same tidy view as everyone else until they ask for more. It hides itself unless the org runs teams or it's already on.
- **Group management is one component** (`GroupsManager`) behind `/admin/groups`, `/@<slug>/settings/groups` and the org's Groups panel on `/admin/orgs`, so the three stay alike. The org page carries the audiences/teams switch next to the list; switching to teams asks first, because members start seeing each other.
- **An org's groups run as teams by default; host groups as audiences.** Orgs mostly want groups to organise people who already work together, and nothing is limited to a team until someone picks one. Host groups gate personal apps across the whole instance, where members needn't know about each other, and existing deployments already relied on audiences there.
- **Adding a group opens a modal** with its name and its members, from an "Add group" button beside the page heading. A name field inline next to the button was rejected: it cluttered the page and left members to a second step.
- **A group has an avatar: an uploaded image, else an icon, else its initials** (`GroupAvatar`). Every list or picker that shows a group shows its avatar beside the name, so a group reads the same everywhere; menu and select items take `avatar: groupAvatarProps(group)` instead of a generic team icon. The image and icon are set in the same modal as the name: Add group opens it empty, the row's Edit opens it filled. An inline rename on the row was replaced by that modal so the avatar and name are edited together.
- **A group's avatar in that modal is the control for its icon and image.** Clicking it opens a popover with an Icon tab (the icon grid) and an Image tab (a drop zone that also opens the file browser, and Remove); an image file dropped anywhere on the form sets the image too. Picking an icon drops the image, so the avatar always shows what was last chosen. Separate "Icon" and "Image" fields under the name were rejected: they sat apart from the preview they changed, and an icon picked while an image was set changed nothing on screen.
- **A person's avatar is changed by clicking it** (`UserAvatarPicker`), on `/admin/users` and an org's Members page: the same popover as a group's Image tab, without the Icon tab, and saved at once since those slideovers have no form to save it with. "Upload avatar" and "Remove avatar" buttons under the name were rejected: they took a row of the header for something rarely changed, and groups and people would have set their picture in two different ways.

## Views and records

- **A view holds tabs, shown in the header row next to its name.** The view keeps the record type, sharing, a base filter and any hand-picked records; each tab picks its own layout (board, list, table or calendar), grouping, card fields, sort and an extra filter ANDed with the view's. "My tasks" is one view with "My open tasks", "By status" and so on as tabs, so one share covers all of them.
  - A separate container object with its own name ("collection", "workspace", "tracker", "page") was rejected: none fit every record type and layout, and people already make views, so tabs inside a view add no new thing to learn.
- **Filters are built in a modal behind a "Filter · N" button** in the tab's toolbar: rules and groups one level deep, each matching all or any. A tab's builder shows the view's base filter read-only above it, since the tab can only narrow it. Edits save to the tab for everyone; people who can only view see the builder read-only.
  - Inline filter chips in the toolbar were rejected: they couldn't express OR, and they mixed personal and saved filters in one row.
  - Readable chips under the tabs were considered and left out for now; the count on the button is the only on-page sign of a filter.
- **The list layout is one row per record with a done checkbox** on types with exactly one closed status; unticking returns the record to its status field's default. Rows drag into a manual order per tab and, when grouped, between sections with the board's move-or-add rules.
- **The calendar layout is a month of whole weeks with each record on the day of a date field** the tab names, or across every day from it to an optional end date field. Records show by name with a status dot, done ones struck through; dragging one to another day changes its dates (the end moves with the start), and each day's "+" adds a record on that day. Records with no date sit in an Unscheduled tray beside the month, to drag onto a day. A calendar has no card fields or saved sort: chips are too small for values, and a day orders by its dates.
  - Placing a calendar card by a hand-set position, as custom board columns do, was rejected: a date on a calendar is the record's date, so moving it anywhere else would show a day the record doesn't have.
- **Who can open a view is set in its Share popover, not shown beside its name.** The popover holds the "Who can see it" checklist (everyone, teams, or ticking nothing for only the owner) and the people it's shared with. The new-view modal has the same checklist. A Private/Shared badge in the header was dropped: it repeated what Share shows and couldn't say which teams.
- **Any board tab can have custom columns, not only a view of hand-picked records.** On a view that shows every matching record, cards nobody has placed sit in a leading "No column" lane, and a new custom-column tab starts with only that lane so people add the columns they want. Moving a card there only moves it on that tab, never the record.
  - Dropping unplaced cards into the first column was rejected: every new record would quietly land in "To do", and sorted cards couldn't be told from ones nobody had looked at.
  - Starting with To do / Doing / Done was rejected for these tabs: a tab beside a status board is for sorting cards your own way, and three stock columns had to be renamed or removed first. A hand-picked view's boards keep them, since its cards always need a column.
- **The new-view and new-tab modals pick the layout and the column mode from cards** with an icon and a name each, in a wider modal with a header and footer. Inline radio buttons made the modals read as one dense block where the choices that shape the view looked like minor options.
- **Permissions live on the record type; views only show or share.** Who can see or change a type's records is decided by the type's Permissions matrix (roles, plus team rows that only add) and by single-record shares. A view that shows every matching record grants nothing: each viewer sees what the type lets them. A hand-picked view shares its cards with everyone who can open it, at their level on the view (Can view reads and comments, Can edit edits), and its editors create cards there and delete the ones created on it. Contacts are never shared through a view.
  - Letting every view grant access to what it shows was rejected: it rebuilt the type's permissions inside every view (create, edit, delete and comment rules per view, an owner check before sharing, access that only applied when you arrived through the view), and anyone who could change a filter could widen what it handed out.
  - So that a team sees every deliverable on a shared view, give the team view_all on the type, not the view.
- **The new-view modal asks what the view holds, as two cards: "Its own cards" or "All <type>".** It starts on "All" for types the person can see all of and on "Its own cards" otherwise, and can't change later. Deriving it from the board's column mode was rejected: lists and tables could never hold their own cards, and nobody could tell which kind they were making.
- **Teams and Everyone get Can view or Can edit like people do**, in the same checklist, with only the owner changing who can open a view or its base filter. Can edit covers the cards and the tabs. A newly picked person, team or Everyone starts at Can edit: sharing a board is nearly always so people can work on it.
  - Starting at Can view was rejected: people added to a board couldn't add or move cards until someone noticed and raised them.
- **Deleting a card created on a hand-picked view deletes the record; any other card only comes off the view.** The card's button and menu say which. Deleting such a view deletes its own cards too, after a dialog that counts them; cards also on another view are kept.
- **The views landing page has two columns by audience: Teams and Mine.** Teams holds every view open to a team or Everyone, including the caller's own, with team avatars or an Everyone badge on each row; Mine holds the caller's private views, with private views others shared with them by name under a "Shared with me" heading. Each column's "+" opens the new-view modal set to that audience (Teams starts on the caller's team, or Everyone when they have none). Sorting by audience means a team's board sits in the same place for everyone on the team.
  - Grouping by owner (everything I made under "My views") was rejected: a shared board appeared in different places for its owner and its team.
  - A third "Shared with me" column and one heading per team in the Teams column were rejected as more places to look than a two-way mine/ours split needs.
  - Tabs and per-group sidebar entries were rejected in favour of seeing both groups at once.
- **The new-view modal opens on "What are you tracking?"**: To-dos, an ideas board, a list of anything, then the org's own record types, plus "Something else". A tile sets the record type, what the view holds and the layout; the name and who can see it come next, and the rest sits under "More options". Asking for a record type first meant nothing to someone making "ways to bake a pizza", and the full form showed six decisions before the first card.
  - Code-shipped templates ("Recipes", "Reading list") were rejected for now in favour of "Copy view": templates then come from boards people actually use, without code.
- **A view's own fields are managed from the view menu ("Fields") and filled in from the card's details**, in a section named after the view at the end of the fields sidebar. Only the owner adds, renames or deletes fields; deleting one asks first, since it removes every value on it. Values show only inside the view.
  - Showing every view's values on the record page was left out for now: a popular record on a dozen lenses would stack a dozen sections of other people's fields.
  - Letting editors manage fields was left out for now; it's one rule change if teams ask for it.
- **A card's cover is the first image on its type's cover field** (items: Attachments), shown across the top of board cards. Other files show as a count.
- **Every record type has a Tags field (`<RecordsFieldsTagsField>`) that can't be hidden, and it suggests the tags already in use as you type**: the tags on that type's records the person can see, most used first. Create appears only when what's typed matches none of them in any case, so "mvp" picks the existing "MVP" rather than adding a second spelling. Free-text chips were rejected because, with nothing suggested, spellings drift and filters miss cards. A fixed multi-select was rejected because only admins could add a tag. Suggestions from every type were rejected because contact tags ("donor") crowded deliverables, and suggestions from records the person can't open were rejected because they would leak a private card's tags.
- **Assigning someone who can't see a record asks first**, in a confirm dialog naming them ("Assign and share"), wherever the assignment happens: the record page, a card's details, a board drag, a new card from a view's filters. Only fields that hand a record over (an assignee) share it; other people fields never do, so mentioning someone on a private card can't leak it.
- **A board or list grouped by status has no "No status" column.** Every record type has a status and a record without a stored one reads as the default, so the column could only ever be empty; dropping a card there is refused. New boards start grouped by status.
- **Built-in views (declared in code, such as My tasks) sit in their own "Built-in" row above the Teams and Mine columns**, with a "Built-in" badge in the view's header. They open read-only for everyone: no tab, filter, sharing or rename controls. Cards still move between status columns, the list's checkbox still works, and quick-add still creates cards, since those change records, not the view. "Copy view" is how someone makes their own version.
  - Creating a "My tasks" row for each person on first visit was rejected: the default would live in the database, so changing it meant a migration, and people with an old copy kept it.
- **A task with subtasks opens as its own board, one level at a time.** On a card or list row the subtasks progress is the way in; clicking anywhere else on the card still opens its details, where the heading of the subtasks list has a "Board" link (so a task with no subtasks yet can be broken down). The link sits with the subtasks rather than among the header's buttons, where an icon alone didn't say what it opened. The board is a parameterized built-in view (`builtin.subtasks.<taskId>`) with a Board tab of the direct subtasks and an All levels tab of everything under the task, and a subtask's own subtasks open the same way.
  - Separate record types for each level (deliverable, task, subtask) were rejected: the depth isn't fixed, a card moves between levels as work is reorganized, and every extra type is another "contains" link for boards, filters and progress to understand.
  - One type above tasks is allowed (see "An org nests one type under another" below): what was rejected is a type per level, not a top level that is a different kind of thing.
  - Showing subtasks nested inside the overview's cards, or as an expanding tree, was rejected: most people only read the overview, and the breakdown is clutter to them.
  - A saved view per big card was rejected: rows to create and keep in step with the tasks, where a built-in works for any task at any depth. "Copy view" makes a saved one for a project that wants its own columns.
  - Making the whole card open the board was rejected: most clicks on the overview want the card's details.
- **An org nests one type under another in the schema builder, with one choice on the connection field**: "No nesting", "They sit under this" or "This sits under them". The team's deliverables go through stages a task doesn't have (Ideas, Waiting on others, Abandoned); with their own type those statuses stay off every task, and a deliverable's card opens a board of its tasks the way a task opens its subtasks.
  - A view-only "Stage" field on the deliverables board was the alternative that needed no code. It was rejected because the stage and the task's status become two things to keep in step: a deliverable moved to Abandoned on the board stays open in its assignee's My tasks.
  - Adding the statuses to the task type was rejected: every task in the org would offer them and every status board would grow the columns.
  - The matching field on the other type is created automatically. Asking the admin to make both halves and keep them pointing at each other was rejected as a way to end up with half a link.
  - The choice is made when the field is created and locked after, like its kind and target. Turning an existing connection into nesting would have to pick one parent per record from links that may hold several.
  - Deleting either half deletes the other and un-nests the records, after a warning in the field editor.
- **That board's header is a trail, not a "Built-in" badge**: the view the person came from, then the records whose boards they went through to get here, then the task itself, which opens the task's details. The starting view rides in `?from=` and the records on the way in `?path=`, both kept on every board below, and the back arrow goes back one step. Without the starting view a deep board had no way back to the overview except the browser's back button. Listing every record above was rejected: a deliverable's board opened from All deliverables led with its Project Class, a step the person never took. A board opened without `?from=` (a shared link) still lists every record above, since there are no steps to show.
- **Moving an existing task under one other people can see asks first** ("Move and share"), in the same dialog as assigning: the task and everything under it become visible to everyone who sees the parent. Creating a subtask there doesn't ask, and neither does a move that puts nothing new above the task. A move between branches of one tree asks when the new branch is shared: the first version skipped every move inside a tree, which let a private subtask slide under a shared sibling unannounced.
- **A record's Share list also shows the access that comes down the tree**: under the direct shares, each task above it that is shared or assigned (with who), and the views holding those tasks ("Through <task>"). Listing only the record's own shares made a subtask under an org-wide card read as private, and made removing a share look like a revoke when the person still saw it from above.
- **On a board grouped by parent task, a drag moves the card**: it leaves the column it came from, since a task has one parent. Adding the new parent beside the old one, as other connection fields do, showed the card in both columns.
- **A board card shows each field as an icon and its value, with the label as the icon's tooltip.** A field without an icon of its own takes its kind's (`recordsFieldIcon`: a calendar for dates, people for people fields), and the status, parent and subtasks fields have theirs. A text label before every value ("Status To do", "Assignee Alice") made a six-field card read as a block of text, half of it words that are the same on every card.
- **A board can keep a card field on its cards while empty, and that field is set from the card.** The Card fields modal gives each field a card can set a "Show when empty" switch, off by default (the tab stores the keys switched on, `cardShowEmpty`). An empty one shows as its icon and "Add <field>"; clicking it, or its value once set, opens the field's own editor (`<RecordsFieldRow>`) in a popover with the picker already open or the cursor in the box (`<ViewsCardFieldPopover>`). A single value closes the popover once picked; lists stay open to add more. Long text, files, status, parent and subtask links, repeat and reminder are set from the card's details, and lists and tables are unchanged. Connections change by the links added and removed, so links the viewer can't see on the card are kept.
  - Making every card field editable from the card was rejected: clicking a value would no longer open the card's details, and the switch already names the fields people fill in on the board.
- **A record's details show every field's icon before its label**, the same icon its card row has, so a field reads the same on the card and in its details. Showing an icon only on fields that set one left Priority and the dates with icons and Status and Assignees without, which read as a mistake.
- **A record's details fill the screen in two columns: the long text (a task's description) with connections and activity in the main part, every other field in a sidebar.** A card on a view opens them as a full-screen dialog over the board, and the record page is the same component (`<RecordsDetailView>`, with `embedded` in the dialog), so there is one details UI. On a narrow screen the sidebar sits between the description and the activity. The dialog's header has Close where the page has its back link, plus "Open as a page".
  - The open card is in the view's URL (`?card=`), so going to a record its description links to and pressing Back returns to the card, and the card's address can be shared. It replaces the history entry instead of adding one, so Back never just closes a card.
  - The records under a record (a task's subtasks) are a list in the main part, under the description: a tick box, the name, who it's assigned to, a line to add another, and how many are done in the heading. Done ones are left out until "Show N done" is pressed, and the list stops at 15 rows with "Show N more", so a long or mostly finished breakdown doesn't push the activity off the screen; the count in the heading still covers all of them. They are work to do, not a property of the task, so they left the sidebar; the parent stays there as a field.
  - A separate "Connections" section that listed every connection field again as chips was removed: each connection field already shows its chips in its own row.
  - A field holding people or linked records is its chips plus a ghost "+", with no select box: the chips are the value, × on a chip removes it, and "+" opens the search. A select box above the chips showed every name twice, and one saying "3 linked" or "1 assignee" above the chips told the reader nothing the chips didn't. Putting the chips inside the select box was rejected because a chip couldn't be removed without opening the menu, and an avatar stack with no names because the sidebar has room for the names. A single person is a ghost button showing them, which opens the search to change them.
  - The narrow slideover it replaces showed every field as a row, so the description was a three-line box squeezed beside its label, and comments were only on the record page.
  - A second, slideover-sized layout kept beside the page was rejected: two UIs for one record had already drifted (only the page asked for a closing reason).
- **An empty field in a record's details is an add button, not a row** (`<RecordsFieldGroup>`). Each sidebar section ends with a wrapping strip of small outline buttons (a plus, the field's icon, its label), one per empty field, in the fields' order; pressing one opens the field as a row with its editor ready (the date picker showing, the people search open, the cursor in the box). A new task showed ten rows with one value among them; now it shows Status and a few lines of buttons. It applies to every record type, in the dialog and on the record's page, and to a view's own fields.
  - Empty means no value, blank text or an empty list. Zero is a value, and so is a "No" someone chose: a yes/no field is a button only until it's first set, and its button sets it to Yes.
  - A row opened from its button and left empty goes back to a button. A row that had a value and was cleared stays until the details are opened again, so replacing a value doesn't send the person down to the strip to find the field.
  - A required field keeps its row while empty, asterisk and all: a missing required value is the one empty field that has to stand out.
  - Reminder and Repeat have no button until the task has a due date, since they count from it. Two greyed-out buttons on every new task were rejected.
  - People who can't edit see only the fields with a value, and a section with none disappears with its heading. The "—" rows told them nothing they could act on.
  - The strip sits at the end of its own section, so a field appears where its button was. Putting the buttons under the title across the main part (where Trello has them) was rejected because the row then appears in the other column; one strip for the whole sidebar was rejected for the same reason.
  - A single "+ Add field" button with a menu was rejected: every add took two clicks and the available fields couldn't be seen without opening it. Capping the strip at a few buttons with "more" was left out for now; all of them wrap.
  - Letting a type pin fields as always shown was rejected as one more setting to explain. Collapsing only some kinds (tags, people, files) was rejected because a new task still showed five or six empty rows.
- **A task's description is rich text** (a `rich_text` field, edited with `<RecordsFieldsRichTextField>`): headings, bulleted and numbered lists, quotes, bold, italic, strikethrough, inline code, links, and links to other cards. The toolbar sits above the text; typing Markdown ("# ", "- ", "**bold**") formats as you go; "#" (or the toolbar's # button) searches every record type the person can read and inserts the pick as a chip that opens that card. Clicking a link opens it, in the editor too; the toolbar's link button takes the URL in a small popover, not `prompt()`. It saves when focus leaves the field, like every other field, and the timeline says only "changed Description".
  - It also has checkbox lists (the toolbar's checklist button, or "[ ] " at the start of a line), "@" to mention a person, and images: paste, drop or pick one and it uploads to the card's Attachments and shows in the text.
  - A mention tells the person, in the app and by email, only if they can already open the card. Sharing the card with whoever is mentioned was rejected: only assigning hands a card over, so a name typed in a private card can't leak it. The person writing isn't told who wasn't notified; that is the gap to close next.
  - While an image uploads, the text shows the local file dimmed and pulsing and a line under the text says "Uploading image…"; a failed upload takes the preview out and says why. With no sign of the upload, a paste looked like it had done nothing.
  - An image in the text and its file in Attachments are one thing: deleting the image deletes the file, and removing the file takes the image out of the text. A file added straight to Attachments, and never shown in the text, is left alone. Leaving them independent was rejected: it left files nobody could see a reason for, and broken images.
  - Stored as Markdown rather than HTML or the editor's JSON: agents and the meetings layer already write descriptions as plain text or Markdown, old descriptions needed no conversion, and there is no HTML to sanitize.
  - "/" opens a menu of everything that can go in: headings, quote, code block, divider, the three kinds of list, an image, a person, a card. Typing after it narrows the list.
  - A chip shows the card's name of the moment. The name saved in the text is only what agents and exports read; a reader who can't open the linked card sees that saved name.
  - A card lists the cards that link to it under "Mentioned in", below its connections, showing only the ones the reader can open. It is left out when there are none.
  - A floating toolbar that appears on selection was rejected for the first version: nobody finds headings or lists that way.
- **A task can be assigned to several people.** Everyone named sees the task and is told about it. On a board grouped by assignee the card sits in each assignee's column, and dragging it swaps the person it was dragged from for the one it lands on.
- **Another app shows a view inside its own page as an embedded panel** (meetings' Tasks tab shows the meeting's tasks through a parameterized built-in view). The panel drops the back button and title, keeps its active tab to itself rather than in the page's URL, and has an "Open in Views" link. Building a separate task list inside each app was rejected: two UIs for the same tasks would drift apart.

## Email admin

- **Mail accounts, domains and suppressions are tables in cards, and a domain's details open in a slideover**, not a page of their own: an admin moves between domains while setting up DNS, and a slideover keeps the list in view. The org settings page shows its one domain's details inline, since an org usually has one.
- **A domain's details are one panel with ruled sections** (Sending, Receiving, Webhooks, Domain key, From domain, Remove). Tabs were rejected because setting up a domain is read top to bottom, and the receiving step depends on sending.
- **The host's accounts table also lists every organization's own accounts, with an Owner column** (Host or the org's name), so a host admin can see which providers orgs send through. The column appears only when an org account exists, since on a host without any it would say "Host" on every row. An org's account opens read-only for the host and has no ⋯ actions; only the org changes it. The environment account carries a "Read-only" badge with a lock.
- **A capability the key hasn't been tested for says "not tested" in its badge** ("Suppression lists not tested"). A dimmed badge with the words only in a tooltip was rejected: dimmed read as "not allowed", and nobody hovers a badge.
- **An account's status is a dot with a label worked out from what its key was seen to do** (Working, Limited key, Can't send, Not tested, Local only), so an admin sees a limited key before adding a domain to it.
- **Adding a domain is one modal: provider (cards), domain, the domain's key, and a "Receive email on this domain" switch that starts off.** A key that belongs to one domain (a Mailgun sending key) is saved on the domain. What the provider account shares across its domains (Mailgun's webhook signing key and region, an SES or SendGrid key) is saved once as an account behind the scenes, named after the provider; the next domain on that provider picks it in a "<Provider> account" select instead of entering it again. A key the provider refuses is removed again, with the error under the fields. Adding the account first on another tab, then the domain, was rejected: an admin thinks of the domain, and Mailgun shows its sending keys next to the domain. Saving a domain's sending key on a shared account was rejected too: a second domain would be offered a key that can't send for it. Mailgun's account-wide API key and the DKIM selector sit under "More options". Next saves the domain for setup by hand and runs a check at once; the domain's panel then opens on what is still missing.
- **A domain's panel shows the key it sends with** (its own sending key, or its account's API key, masked) and what that key can do. An account that holds no key of its own lists no capability badges: they could never be tested, and "not tested" there read as something left to do.
- **The Email page opens on Domains, and Accounts is the last tab.** Adding a domain saves its provider key, so an admin no longer starts by adding an account; the Accounts tab is where keys are rotated, checked or shared across domains. The "Mail isn't configured" prompt sits in the empty Domains list for the same reason.
- **Setup at the provider is a checklist a person can do.** Each step says where to click at the provider and carries the values to paste; a step the last check confirmed shows a green tick and folds its instructions away, one still missing shows an amber mark with what is missing. The checks read the provider with the key (Mailgun's domain, DNS verdicts, webhooks and routes) and change nothing. A choice between automatic and manual setup before anything was checked was rejected: most keys aren't Admin keys, and hosts don't want an Admin key stored on a website.
- **"Set it up for me" appears only when the key is known to allow it** (for Mailgun, an Admin key), and asks first, naming what it will change at the provider. Showing it to every key and letting the refusal fall back was rejected: the button would fail for almost everyone.
- **A provider's caveats show as an (i) wherever the admin picks it or sets a domain up on it**: the account's Provider field, the add-domain Send through / Receive through fields, and the Sending / Receiving headings of a domain's details (SES's sandbox and receiving regions, SendGrid's unsigned Inbound Parse). Keeping them only in the manual steps was rejected: a domain set up automatically never shows those steps.
- **A role whose automatic setup failed shows that role's manual steps and Verify button**, while the other role keeps its DNS table. Choosing records or steps for the whole domain left a refused role saying "follow the steps below" with no steps.
- **The MX warning and the last check's ticks stay for the session** (kept per domain in client state), so closing and reopening a domain's panel doesn't lose them. Missing SPF, DKIM or DMARC records show as a warning triangle, not a red cross: they don't fail sending.
- **A lapsed domain has one banner, with Check now in it**, inside the domain's details. A second banner on the org page repeated it without the button.
- **Stop receiving is an outlined error button behind a confirm**, like every destructive action; a neutral link made it look as harmless as Change.
- **The accounts organizations' domains are set up on are settings rows with Change**, opening a select with Save and Cancel under the row. Selects that saved as soon as they changed were rejected: settings forms stay closed until the admin acts, and this choice applies to every org domain added afterwards.
- **Org pages call adding an account "Use our own provider account"**, the words an org admin would use; "Add account" stays on the host's page.
- **`/admin/orgs` marks an org whose mail drew spam complaints in the last 30 days with a warning badge** ("3 complaints"). Org domains on the host's accounts share the host's reputation, so this is where a host admin notices. A count on every row was rejected: almost every row would read 0.
- **The Streams tab saves as one form with a save bar**, because changing a stream's domain changes which webhook events the domain needs, and an admin usually moves several streams together.
- **An org sees webhook URLs only for its own provider accounts.** The URLs carry the account's token, so on the host's accounts they stay with the host admin.
